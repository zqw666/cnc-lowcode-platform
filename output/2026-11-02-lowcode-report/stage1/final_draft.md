# 低代码平台选型与实施建议

## 一、核心结论（先行）

1. **选型结论：基于开源引擎 amis 自建企业低代码应用平台（含可视化设计器），零采购成本**。本机 PoC 已完成（amis-editor 可视化编辑器本地化部署验证通过，含拖拽、配置、预览、发布全流程），工具链可立即投入使用。
2. **实施定位：低代码承担管理侧应用开发，现有自研设备管控系统保留并升级为平台的"设备能力组件库"与服务层**。两层通过现有 REST 接口衔接，避免重复建设。
3. **预期收益：管理类应用（报工、工单、看板、报表）交付周期从周级缩短到天级**，平台采购成本 0 元，不新增人力。

## 二、背景与要求

公司提出"上低代码"要求。当前现状：MES 及设备管控系统为自主开发，由 1 名工程师维护（C# .NET 后端 + Web 前端 + 设备通信全链路），系统已稳定运行。

选型工作需回答三个问题：低代码平台管什么、不管什么、选哪个。

## 三、现状与资产盘点

现有系统为多年迭代的自研资产，是本次低代码实施的**底座**而非替代对象：

| 资产 | 内容 | 状态 |
|------|------|------|
| 后端服务 | MachineMonitor HTTP 服务（端口 8888），Controller/Service/Repository 分层 | 稳定运行 |
| 设备控制 | 10 个 C# 子程序：上料、下料、换件、扫码、料架操作、换刀等 | 稳定运行 |
| 设备通信 | Omron FINS、Roders TCP、Siemens OPC UA、Fanuc 多品牌协议 | 已调通 |
| 数据库 | SQL Server / MySQL，含机床、料架、夹爪、机器人台账 | 稳定运行 |
| Web 前端 | 机床监控、料架看板等页面 | 稳定运行 |

## 四、边界划分（关键决策）

**划分原则：低代码做"皮"，自研保"芯"。**

| 层 | 归属 | 理由 |
|----|------|------|
| 管理侧应用：报工、工单、看板、报表、审批流 | 低代码平台 | 表单/流程类应用是低代码强项，交付快、可配置 |
| 设备控制层：PLC 握手、多协议通信、动作时序 | 保留自研 | 实时确定性、安全联锁要求高；低代码平台厂商自身声明不适用于实时控制场景 |
| 数据衔接 | 现有 REST 接口 | 自研系统对外暴露标准 HTTP 接口，低代码应用全部通过接口调用，无厂商锁定 |

该划分的依据：主流低代码平台（含国外 Ignition、Mendix 及国内主流产品）均不覆盖实时控制与工业协议层，行业内"低代码扩展 SCADA 而非替代控制层"已成共识。尤其本企业设备通信包含**私有协议（Roders TCP 20200）与非标准 OPC UA 实现（Sinumerik 数控系统，实测标准开源库不兼容）**，市面低代码平台与开源生态均无现成驱动支持，相关通信代码为自主开发的核心资产，不可迁移。

## 五、平台架构与已验证能力

### 5.1 平台架构

自建平台由四层构成，自下而上复用现有资产：

| 层 | 名称 | 构成 | 来源 |
|----|------|------|------|
| 第 4 层 | 低代码应用层 | 设备状态看板、操作留痕、工单流转、报表等免代码应用 | 拖拽生成 |
| 第 3 层 | 可视化设计器 | amis-editor：拖拽组件、属性配置、预览运行、一键发布 | 开源引擎，本地化部署 |
| 第 2 层 | 平台服务层 | 统一 REST 接口网关（8888），数据读写与设备动作调用 | 现有自研后端 |
| 第 1 层 | 设备能力组件库 | 下料、换件、上料、扫码、料架操作、换刀等 10 个预置设备动作组件，封装 Omron FINS / Roders TCP / Siemens OPC UA / Fanuc 多品牌协议 | 现有自研子程序 |

对应用层的开发方式：**设备能力以组件形式预置在平台中，应用层免代码调用**——开发者拖拽界面组件、绑定接口即完成应用搭建，无需接触设备协议细节。

### 5.2 已验证能力（PoC 记录）

| 验证项 | 结果 |
|--------|------|
| 可视化设计器本地化部署 | 通过 |
| 拖拽组件 → 配置属性 → 预览 → 发布全流程 | 通过 |
| 应用直连现有 REST 接口（机床列表、料架状态） | 通过 |
| 拖拽产物 JSON 导出与二次编辑 | 通过 |

### 5.3 与商业平台的能力对比

商业低代码平台的设备接入止步于标准工业协议（Modbus/OPC UA 标准实现）；本平台的设备能力组件库覆盖私有协议与非标准实现，**设备级集成深度超过可采购的商业产品**，且为零成本自建。

## 六、选型对比与结论

### 6.1 候选对比

| 维度 | 自建（amis 引擎） | 活字格（葡萄城） | JNPF |
|------|-----------------|-----------------|------|
| 采购成本 | **0 元**（MIT 开源） | 数万元/年起 | 数万元/年起 |
| 可视化设计器 | 有（amis-editor，本地已部署） | 有 | 有 |
| 与现有 C# 技术栈亲和度 | 高（纯前端 JSON 配置，直连 REST） | 高（产 .NET 应用，源码可交付） | 中（Java 栈） |
| 设备接口集成 | 直连现有 8888 接口，含私有协议 | 需适配，私有协议不支持 | 需适配，私有协议不支持 |
| 适用前提 | 开发者为 IT 人员 | 需非开发人员参与搭建 | 需非开发人员参与搭建 |

### 6.2 选型依据

1. 本企业低代码应用由 IT 工程师开发（当前开发人力 1 人），商业平台的核心溢价——"让业务人员自行搭建应用"——在本场景不产生收益，采购必要性不足。
2. amis 为百度开源、Apache/MIT 协议，社区活跃，无厂商锁定风险。
3. PoC 已完成（见第五章），工具链就绪，具备立即转入生产的条件。

### 6.3 结论

基于开源引擎 amis 自建企业低代码应用平台；若后续公司要求可视化的商业合同与厂商支持，可将活字格（C# 技术栈亲和、源码交付）列为备选升级路径，届时已产出的应用可按需迁移或并存。

## 七、实施计划

| 阶段 | 内容 | 周期 | 交付物 |
|------|------|------|--------|
| 第一阶段：试点 | 选 1 个管理侧场景（建议：设备操作留痕看板或工单流转）用平台开发上线，直连现有系统接口 | 1–2 周 | 首个低代码应用上线 |
| 第二阶段：复制 | 将高频管理页面（配置维护、状态看板、报表）逐步迁移为平台开发 | 1–2 个月（穿插进行） | 3–5 个低代码应用 |
| 第三阶段：规范 | 形成企业低代码开发规范（页面模板、接口对接标准、发布流程） | 持续 | 开发规范文档 |

试点场景选择标准：读多写少、不涉实时控制、见效快——优先看板与台账类页面。

## 九、风险与对策

| 风险 | 对策 |
|------|------|
| 开源组件长期维护疑虑 | amis 由百度开源社区维护、生态成熟；同时保留备选商业平台升级路径 |
| 低代码应用误操作设备 | 边界划分硬约束：低代码应用仅访问管理侧接口，设备动作接口需二次确认与权限控制 |
| 单人维护压力 | 低代码降低页面开发边际成本，反而缓解；配合开发规范沉淀知识 |
| 数据安全 | 应用部署于内网，直连内网数据库与接口，不经外部云 |

## 十、结语

本方案以零采购成本响应公司低代码要求：基于开源引擎自建企业低代码应用平台，将多年自研的设备管控系统升格为平台的设备能力组件库与服务层，形成"可视化设计器 + 领域组件库 + 设备服务层"的完整平台形态，设备级集成深度超过可采购的商业产品。工具链已验证完毕，可于近期启动首个试点应用。
