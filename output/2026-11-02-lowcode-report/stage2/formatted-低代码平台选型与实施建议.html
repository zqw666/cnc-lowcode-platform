一、核心结论

  1. 选型结论：基于开源引擎 amis 自建企业低代码应用平台（含可视化设计器），零采购成本。本机 PoC 已完成（amis-editor 可视化编辑器本地化部署验证通过，含拖拽、配置、预览、发布全流程），工具链可立即投入使用。
  2. 实施定位：低代码承担管理侧应用开发，现有自研设备管控系统保留并升级为平台的"设备能力组件库"与服务层。两层通过现有 REST 接口衔接，避免重复建设。
  3. 预期收益：管理类应用（报工、工单、看板、报表）交付周期从周级缩短到天级，平台采购成本 0 元，不新增人力。

二、背景与要求

公司提出"上低代码"要求。当前现状：MES 及设备管控系统为自主开发，由 1 名工程师维护（C# .NET 后端 + Web 前端 + 设备通信全链路），系统已稳定运行。

选型工作需回答三个问题：低代码平台管什么、不管什么、选哪个。

四、边界划分（关键决策）

划分原则：低代码做"皮"，自研保"芯"。

层归属理由
管理侧应用：报工、工单、看板、报表、审批流低代码平台表单/流程类应用是低代码强项，交付快、可配置
设备控制层：PLC 握手、多协议通信、动作时序保留自研实时确定性、安全联锁要求高；低代码平台厂商自身声明不适用于实时控制场景
数据衔接现有 REST 接口自研系统对外暴露标准 HTTP 接口，低代码应用全部通过接口调用，无厂商锁定

该划分的依据：主流低代码平台（含国外 Ignition、Mendix 及国内主流产品）均不覆盖实时控制与工业协议层，行业内"低代码扩展 SCADA 而非替代控制层"已成共识。尤其本企业设备通信包含私有协议（Roders TCP 20200）与非标准 OPC UA 实现（Sinumerik 数控系统，实测标准开源库不兼容），市面低代码平台与开源生态均无现成驱动支持，相关通信代码为自主开发的核心资产，不可迁移。

五、平台架构与已验证能力

5.1 平台架构

自建平台由四层构成，自下而上复用现有资产：

层名称构成来源
第 4 层低代码应用层设备状态看板、操作留痕、工单流转、报表等免代码应用拖拽生成
第 3 层可视化设计器amis-editor：拖拽组件、属性配置、预览运行、一键发布开源引擎，本地化部署
第 2 层平台服务层统一 REST 接口网关（8888），数据读写与设备动作调用现有自研后端
第 1 层设备能力组件库下料、换件、上料、扫码、料架操作、换刀等 10 个预置设备动作组件，封装 Omron FINS / Roders TCP / Siemens OPC UA / Fanuc 多品牌协议现有自研子程序

对应用层的开发方式：设备能力以组件形式预置在平台中，应用层免代码调用——开发者拖拽界面组件、绑定接口即完成应用搭建，无需接触设备协议细节。

5.3 与商业平台的能力对比

商业低代码平台的设备接入止步于标准工业协议（Modbus / OPC UA 标准实现）；本平台的设备能力组件库覆盖私有协议与非标准实现，设备级集成深度超过可采购的商业产品，且为零成本自建。

6.2 选型依据

  1. 本企业低代码应用由 IT 工程师开发（当前开发人力 1 人），商业平台的核心溢价——"让业务人员自行搭建应用"——在本场景不产生收益，采购必要性不足。
  2. amis 为百度开源、Apache/MIT 协议，社区活跃，无厂商锁定风险。
  3. PoC 已完成（见第五章），工具链就绪，具备立即转入生产的条件。

6.3 结论

基于开源引擎 amis 自建企业低代码应用平台；若后续公司要求可视化的商业合同与厂商支持，可将活字格（C# 技术栈亲和、源码交付）列为备选升级路径，届时已产出的应用可按需迁移或并存。
